Images: Why Sites Are Slow

Lesson 8 · media · ~8 min

The median web page ships a couple of megabytes, and images are most of it. Not JavaScript, not CSS — pictures. Which makes media handling the highest-leverage performance skill on the web, and one of the most mechanical: a handful of boring decisions, each worth more than a month of code optimization. You may have noticed this site has no images at all; by the end of this lesson that will read as a decision rather than an absence.

The element, done properly

<img src="cat.jpg"
     alt="A grey cat asleep on a laptop keyboard"
     width="1200" height="800"
     loading="lazy">

Every attribute is carrying weight:

  • alt — what the image means, for screen readers, broken connections, and search engines. The test: if the image vanished and its alt text appeared instead, would the page still make sense? Decorative flourishes get alt="" — empty, but present — so screen readers know to skip them rather than announce a mystery.
  • width and height — not for display size (CSS controls that) but for shape. They let the browser reserve the right space before the image loads. Omit them and you get the web's most hated experience: text that jumps just as you tap it, because an image above finally arrived. The metric is called Cumulative Layout Shift; the fix is two attributes.
  • loading="lazy" — below-the-fold images wait until the reader scrolls near them. Free bandwidth savings, one attribute, no JavaScript. (The old way was an entire library.)

Four formats cover everything

  • JPEG — photographs. Lossy, small, thirty years old, still fine.
  • PNG — screenshots, flat graphics, and anything needing transparency. Lossless, so photos-as-PNG are the classic 10× size mistake.
  • SVG — icons, logos, diagrams. Not pixels but instructions: text markup, infinitely scalable, usually tiny, styleable with CSS. More below.
  • WebP / AVIF — modern replacements that make JPEGs 30–50% smaller at the same quality. Universally supported now; the only reason the web is still full of JPEGs is inertia.

Don't send a billboard to a phone

A 4000-pixel-wide photo displayed in a 350-pixel column is about 90% wasted bytes — the single most common image mistake. The boring fix is srcset: list the same image at several widths and let the browser pick the smallest sufficient one for the actual device: 

<img src="cat-800.jpg"
     srcset="cat-400.jpg 400w,
             cat-800.jpg 800w,
             cat-1600.jpg 1600w"
     sizes="(min-width: 40rem) 65ch, 100vw"
     alt="...">

The browser knows the screen, the pixel density, and eventually even the connection quality — decisions you couldn't make server-side if you tried. You just have to offer the options. One flexible-width CSS rule completes the setup, and this site's stylesheet now includes it: images never overflow their column (max-width: 100%).

The boring truth: the fastest image is the one you don't send. This site's pages are a few kilobytes each — they load instantly on a bad connection not because of clever engineering but because text is the most optimized format ever shipped. Every image earns its bytes or doesn't board. The same judgment, applied with less rigor, is why the median page is a hundred times heavier than it needs to be.

Video and audio, briefly

<video controls> and <audio controls> give you native players — play, pause, scrub, fullscreen, captions via <track> — with no library. The one non-obvious move: never autoplay with sound (browsers block it anyway), and give videos the poster attribute so something sensible shows before play. Hosting video files is the point where "boring" means use someone else's infrastructure — video delivery is a genuinely hard problem, and embedding is usually the right rung.

Check yourself

Why set width and height on images when CSS controls display size anyway?

They give the browser the image's proportions before it loads, so space gets reserved and the page doesn't jump when the image arrives — eliminating layout shift.

Photo of a sunset, company logo, screenshot of an error dialog: which format for each?

Sunset: JPEG (or better, WebP/AVIF) — lossy suits photos. Logo: SVG — scalable, tiny, CSS-styleable. Screenshot: PNG — lossless keeps text crisp (JPEG artifacts smear sharp edges).

What problem does srcset solve, and why is the browser the right decision-maker?

It stops phones from downloading desktop-sized images by offering multiple widths. The browser picks, because only it knows the device's screen size, pixel density, and connection — things the server can't reliably see.

When is alt="" (empty) correct, and how is it different from omitting alt?

Empty alt marks an image as decorative, telling screen readers to skip it silently. A missing alt attribute leaves them to announce the filename — noise that helps no one.
