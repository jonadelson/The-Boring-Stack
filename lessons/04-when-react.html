When Do You Actually Need React?

Lesson 4 · architecture · ~7 min

The boring stack is not anti-JavaScript, and it is not anti-React. It's anti-default. React is a genuinely great tool that has become the reflexive starting point for every website, including the large majority that don't need it. The skill this lesson teaches is telling the difference — and the vocabulary for it is a ladder.

The interactivity ladder

Interactivity isn't a yes/no question. It's an escalation, and each rung costs more than the one below — in tooling, in payload, in failure modes, in things you must now do yourself (routing, focus management, browser history) that the platform did for free.

  1. HTML and CSS alone. More interactive than its reputation: <details> disclosure, <dialog> modals, form validation, CSS transitions, hover and focus states, scroll snapping. This site is currently on this rung — including its quizzes.
  2. JavaScript sprinkles. Server-rendered pages plus small scripts for specific behaviors: remember a preference, filter a list, enhance a form. The page works without them; the script makes it nicer. This is "progressive enhancement," and it powered most of the useful web for fifteen years.
  3. HTML over the wire. Tools like htmx or Turbo: user actions fetch fragments of server-rendered HTML and swap them into the page. You get SPA-feeling updates while the server remains the single source of truth — no client-side state to synchronize. A large share of "we need React for this" apps live comfortably here.
  4. Islands. A mostly-boring page with one genuinely rich component embedded in it — a chart, an editor, a map. Use a framework inside the island if it earns its keep; the rest of the page stays on the lower rungs.
  5. Full client-side application. The framework owns the page: state, routing, rendering. Sometimes this is exactly right — see below.

The boring truth: the ladder is climbed per problem, not per project. A site can be rung 1 almost everywhere, rung 2 in a few places, and rung 4 on the one screen that needs it. The mistake is starting every project on rung 5 because that's where the tooling defaults are.

Documents versus tools

The most useful heuristic for picking a rung: is this screen a document or a tool?

A document is content you read and forms you submit: articles, product pages, dashboards, admin panels, checkout flows, settings screens. State lives on the server; the page is a view of it. Documents belong on rungs 1–3, and browsers are spectacularly good at them — instant back button, working links, free accessibility, no loading spinners for content that's just text.

A tool is continuous manipulation of live state: Figma, Google Sheets, a video editor, a multiplayer game, a collaborative whiteboard. Feedback loops are measured in milliseconds, state changes dozens of times between server round trips, and the interaction is the product. Tools genuinely need rungs 4–5, and React (or something like it) is the right call — hand-managing that much DOM state without a framework is how frameworks got invented.

The uncomfortable observation: most React apps in production are documents wearing a tool's architecture. A settings page with four forms doesn't need client-side state management — it needs <form>. The test is not "does it have interactivity?" (everything does) but "does the interactivity outrun what the lower rungs provide?"

Why learning the boring rungs makes you better at React

React is a layer over the platform: components render to the DOM, events are DOM events, effects wrap the same lifecycle the browser exposes, and every fetch is still HTTP with the same caching, cookies, and failure modes. Developers who only know the framework struggle precisely where the abstraction leaks — focus management, scroll restoration, why the back button broke, why the form doesn't submit on Enter. Learning the platform underneath isn't a detour from React skills; it's where the hard React bugs get solved.

What this site will do about it

This site will climb the ladder rung by rung, on camera. It's on rung 1 now. Phase 2 adds rung-2 sprinkles (quizzes that remember your answers). Later phases will hit real problems — syncing state, richer widgets — and each time, the lesson will be whether the next rung is earned or whether the current one still holds.

Check yourself

What's the "documents versus tools" test?

Ask whether the screen is content-and-forms with server-owned state (a document — rungs 1–3) or continuous manipulation of live state where the interaction is the product (a tool — rungs 4–5, where frameworks earn their cost).

Your app needs one rich, stateful chart on an otherwise ordinary page. Which rung?

Rung 4 — an island. The chart can use whatever richness it needs while the rest of the page stays server-rendered HTML.

Name two things the browser does for free on rungs 1–3 that a full SPA must reimplement.

Any two of: working back/forward history, link behavior, scroll restoration, focus management, form submission and validation, "loading" states (the browser's own progress indicator), accessibility semantics.
