Forms: The Most Underrated Element

Lesson 6 · html · ~8 min

Before JavaScript could do anything useful, the web already had search engines, shopping carts, forums, and webmail. All of it ran on one element: <form>. The form is the original write path of the web — the way a page stops being a document you read and becomes a request you compose. It is also, in modern framework code, the most commonly reimplemented-badly piece of the platform.

The anatomy

<form action="/search" method="get">
  <label for="q">Search</label>
  <input id="q" name="q" type="search">
  <button>Go</button>
</form>

Three attributes do all the work:

  • action — the URL the request goes to.
  • method — get or post (more below).
  • name — on each input. This is the one people forget: only named inputs are submitted. The name becomes the key, the value becomes the value. A form is a little key-value editor for building an HTTP request.

And note the <label> with for pointing at the input's id: that link means screen readers announce the field's purpose, and — the part everyone appreciates — tapping the label focuses the input. On a phone, that turns a tiny checkbox into a big target.

GET or POST: the question that organizes the web

This is lesson 5's request anatomy put to work. A GET form encodes the fields into the URL's query string: /search?q=postgres. The request has no body and no side effects — which is exactly why the result can be bookmarked, shared, cached, and safely retried. Every search results page you've ever linked to someone works because search is a GET form.

A POST form puts the fields in the request body and means do something: create the account, charge the card, publish the comment. Browsers treat it accordingly — ever seen the "resubmit form?" warning when tapping back? That's the browser protecting you from repeating a side effect. (Servers dodge that dialog with a boring trick called Post/Redirect/Get: answer every successful POST with a redirect, so reloading the result page re-runs a harmless GET. You'll implement it in phase 3.)

The rule is one sentence: reading is GET, changing is POST. A shocking number of real-world bugs — search pages you can't share, crawlers deleting records by following links — are violations of that sentence.

Try it — no server required

This form GETs to this very page. Type something, submit, and watch the URL: your input becomes a query string, the page reloads, and you've composed an HTTP request by hand.

Try submitting it empty, too. The browser refuses and explains why — that's required and minlength at work, with zero JavaScript.

Validation the platform already does

  • required — must be filled
  • type="email", type="url" — must look like one
  • minlength, maxlength, min, max — bounds
  • pattern — a regex, for everything else

The browser blocks submission, focuses the offending field, and shows a message in the user's own language. CSS can style invalid fields via the :invalid and :user-invalid selectors. One caveat that phase 4 will drill in: client-side validation is a courtesy to honest users, not a defense — anyone can send any request to your server, so the server must validate everything again.

The phone keyboard trick

The type attribute changes which keyboard a phone shows: email surfaces the @, tel shows a dial pad, number shows digits, date opens a native date picker. Combined with autocomplete hints (autocomplete="email", "name", "one-time-code"), the browser will fill most forms for the user. This is the cheapest mobile UX improvement in existence, and it's a few characters of HTML.

The boring truth: a plain HTML form submits on Enter, validates itself, works with every password manager and autofill system, and needs zero code. Framework apps that rebuild forms as controlled components plus onClick handlers routinely lose those behaviors one by one — then reinstall them as libraries. When a form on a React site won't submit on Enter, you're watching this lesson's absence.

Where this goes

Forms are the write path for the rest of the roadmap: in phase 3, a form is how quiz answers reach the server; in phase 4, login is a POST form, and most web security is the discipline of handling form input safely. The element you just met is the surface area of everything that follows.

Check yourself

Why does an input without a name attribute do nothing?

Because submission serializes name/value pairs — the name is the key in the request. No name, no key, nothing sent.

Search results, delete-account button: which method for each, and why?

Search is GET — no side effects, so the URL is shareable and safely repeatable. Deleting is POST — it changes things, so it must not live behind a link a crawler or a reload could re-trigger. Reading is GET; changing is POST.

Your form has required and pattern on every field. Is server-side validation still necessary?

Absolutely. Browser validation only constrains people using your form politely — anyone can craft a raw HTTP request with any payload. The server must re-validate everything.

What does type="email" buy you on a phone?

An email-shaped keyboard (with @ handy), basic format validation, and — with autocomplete="email" — autofill from the browser.
