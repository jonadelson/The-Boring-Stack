The DOM and Events: Your First Sprinkle

Lesson 10 · javascript · ~9 min

Phase 2 begins, and something changed on this site today: the quizzes remember. Scroll down, reveal an answer, tap "Got it," and reload the page — the check mark survives. The feature is about sixty lines of vanilla JavaScript in a file called js/quiz.js, and this lesson is a guided tour of it. Open the two side by side if you can; everything below is in that file.

The DOM: your page as a live data structure

When the browser reads your HTML, it builds the Document Object Model — a tree of objects, one per element, that JavaScript can inspect and change. The crucial word is live: the HTML file is the blueprint, but the DOM is the building, and changing the building doesn't touch the blueprint. That's why "view source" (the file) and the browser dev tools' element inspector (the DOM) can disagree — and after today, on this site, they do: the grading buttons below exist in no HTML file. They're built at load time, out of nothing.

Finding things: your CSS knowledge, reused

const quiz = document.querySelector('.quiz');
const questions = quiz.querySelectorAll('details');

querySelector takes a CSS selector — the same language you learned for styling — and returns the first match; querySelectorAll returns all of them. This is most of DOM-finding in practice, and it means every selector skill from lesson 3 transfers directly. (There's a subtlety our script steps around: querySelectorAll returns a NodeList, an array-like — spreading it, [...​], produces a true array with the full toolkit of filter and friends.)

Making things

const button = document.createElement('button');
button.textContent = 'Got it';
controls.append(button);

Create an element, fill it, attach it — the node appears on screen the moment it's appended. Note textContent, not innerHTML: it treats the string as text, never as markup. With our own button labels the difference is invisible, but the habit is load-bearing — innerHTML with data you didn't write is how sites get scripts injected into them, and phase 4 has a whole lesson on that disaster. Default to the boring property.

Events: the page talks back

button.addEventListener('click', () => {
  progress[keyFor(index)] = { result, at: new Date().toISOString() };
  saveAll(progress);
  renderQuestion(details, index);
  renderTally();
});

The DOM is also how the page reports what the user does. Every tap, key, scroll, and submit fires an event; addEventListener registers a function to run when one happens. This is the whole interaction model of the web — every framework's onClick is this, one layer down. Our listener does four things, and the order is the lesson: change the data, save the data, then re-render the affected pieces from the data. State first, appearance second — the appearance is always derived. Keep that discipline and sprinkles stay manageable; lose it and you get pages where the screen and the truth drift apart.

Notice also the division of labor at the render step: JavaScript only stamps a data-result attribute on the element. The ✓ and ✗ marks are drawn by CSS rules keyed to that attribute. JS owns state, CSS owns appearance — each layer doing the job it's best at.

Loading: one attribute, no ceremony

<script src="../js/quiz.js" defer></script>

defer tells the browser: fetch this without blocking, run it after the document is parsed. That guarantee is why the script can touch the quiz without wrapping everything in load-event boilerplate — by the time it runs, the elements exist. This one attribute replaces a folder of build tooling for a site this size.

The boring truth: you just read the framework-shaped hole. Find elements, create elements, listen, keep state, re-render from state — that loop is what React abstracts, and at sprinkle scale the abstraction costs more than the loop. The skill of the ladder's rung 2 is recognizing which scale you're at. When the re-rendering gets genuinely hairy — many views of the same state, updates cascading — that's rung 4 knocking. A quiz tally is not that day.

Where the memory lives (and its two limits)

Persistence comes from localStorage — a tiny key-value store the browser keeps per site, surviving reloads and restarts. It gets its own lesson next, but two limits are worth naming now because we chose them deliberately. It stores only strings (hence the JSON encoding at the borders). And it belongs to this browser on this device — your phone's progress will never appear on your laptop. That second limit is not a bug in our code; it is the wall you must hit before a server is earned. We are now, officially, walking toward the phase 3 pain on purpose.

Try it

Grade the quiz below, reload, and watch the marks persist. Then the fun one: open this page in a private/incognito tab — blank slate, because private tabs get their own throwaway storage. If you're at a desktop, the console (F12) will show you localStorage.getItem('boring-stack:quiz') — your answers, sitting there as JSON.

Check yourself

Why can "view source" and the dev tools' element inspector show different content?

View source shows the HTML file as delivered; the inspector shows the live DOM, which scripts may have changed since. This page's grading buttons exist only in the second.

Why prefer textContent over innerHTML?

textContent treats input as inert text; innerHTML parses it as markup, which turns any not-fully-trusted string into a script-injection risk. Default to text.

In the click listener, why does saving happen before rendering?

The discipline is state-first: change and persist the data, then re-render the display from the data. The screen is always a derivation of stored truth, so they can't drift apart.

What does defer promise, and what boilerplate does it remove?

The script downloads without blocking and runs only after the document is parsed — so the elements it needs are guaranteed to exist, without wrapping code in load-event handlers.
