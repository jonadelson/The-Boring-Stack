SQL From Zero

Lesson 16 · postgres · ~10 min

SQL was designed in 1974. Postgres began at Berkeley in 1986. Both predate the web itself, and both will outlive every technology in your current job listing — SQL is the oldest still-dominant language in software, and learning it is the single best effort-to-longevity trade this roadmap offers. Every query below was really executed in Postgres 16; the repo carries the whole tour as server/db/sql-from-zero.sql, runnable end to end. The domain is this site's own future: questions and their reviews, the data our spaced-repetition engine will keep in Postgres once sync arrives.

A table is a contract

CREATE TABLE reviews (
  id          integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  question_id integer NOT NULL REFERENCES questions (id),
  result      text NOT NULL CHECK (result IN ('right', 'wrong')),
  reviewed_at timestamptz NOT NULL,
  next_due    date NOT NULL
);

Compare this to localStorage, which stored whatever string we handed it. A table declares the shape of every row — and the database enforces the declaration. Each line is a promise: NOT NULL (this field always exists), REFERENCES questions (id) (every review points at a question that's really there), CHECK (only these two values, ever), PRIMARY KEY with a database-generated id (every row addressable, no two alike). The types matter too — timestamptz is "a moment in time, timezone-aware," a whole class of bugs prevented by a column type.

Asking questions: SELECT

SQL is declarative: you describe the answer you want, and the database decides how to get it — a genuine contrast with the filter/map loops we hand-wrote in JavaScript. Columns are chosen by SELECT, rows by WHERE: 

SELECT prompt, lesson FROM questions WHERE lesson = 'http';

                     prompt                     | lesson
------------------------------------------------+--------
 What does it mean that HTTP is stateless?      | http
 What is the difference between HTTP and HTTPS? | http
(2 rows)

Sorting and limiting compose on the end — the newest three reviews:

SELECT question_id, result, reviewed_at
FROM reviews ORDER BY reviewed_at DESC LIMIT 3;

 question_id | result |      reviewed_at
-------------+--------+------------------------
           4 | right  | 2026-07-30 08:01:00+00
           2 | wrong  | 2026-07-30 07:55:00+00
           3 | right  | 2026-07-28 21:03:00+00
(3 rows)

And GROUP BY collapses rows into facts about rows:

SELECT result, count(*) FROM reviews GROUP BY result;

 result | count
--------+-------
 wrong  |     2
 right  |     4
(2 rows)

The join: why rows hold IDs, not copies

Notice that reviews store question_id, never the question's text. One copy of each fact, referenced everywhere it's needed — the same don't-duplicate discipline this site keeps preaching, formalized as normalization. The JOIN is what reunites the pieces: here, everything due on or before August 1st, with prompts attached: 

SELECT q.prompt, r.next_due
FROM reviews AS r
JOIN questions AS q ON q.id = r.question_id
WHERE r.next_due <= '2026-08-01'
ORDER BY r.next_due;

                     prompt                     |  next_due
------------------------------------------------+------------
 What does it mean that HTTP is stateless?      | 2026-07-26
 What is the difference between HTTP and HTTPS? | 2026-07-26
 Why does an unnamed input submit nothing?      | 2026-07-29
 What is the difference between HTTP and HTTPS? | 2026-07-30
 What does it mean that HTTP is stateless?      | 2026-08-01
(5 rows)

Read the ON clause as the seam: for each review, find the question whose id matches, and staple the rows together. And look closely at the result, because it's subtly wrong for our purposes: questions appear once per review, not once with their latest due date — question 1's August 1st row should supersede its July 26th one. The query did what we said, not what we meant. Saying what we mean takes schema thinking, and that's the next lesson.

Constraints earn their keep by saying no

Both of these inserts were really attempted. The database's answers are the feature:

INSERT INTO reviews (question_id, result, reviewed_at, next_due)
  VALUES (99, 'right', now(), '2026-08-02');

ERROR:  insert or update on table "reviews" violates foreign key
        constraint "reviews_question_id_fkey"
DETAIL: Key (question_id)=(99) is not present in table "questions".

INSERT INTO reviews (question_id, result, reviewed_at, next_due)
  VALUES (1, 'maybe', now(), '2026-08-02');

ERROR:  new row for relation "reviews" violates check constraint
        "reviews_result_check"
DETAIL: Failing row contains (8, 1, maybe, ..., 2026-08-02).

No review of a nonexistent question, no result outside the contract — ever, no matter which buggy code or hurried human tries. In localStorage, both of these would have saved silently and detonated later. The boring principle: push your invariants into the layer that cannot be bypassed. Application code asks nicely; the database enforces.

The boring truth: the industry has spent twenty years announcing SQL's replacement — object databases, XML databases, the NoSQL wave — and every round ended the same way: the challengers grew SQL layers, and Postgres absorbed the challengers' best tricks (JSON columns, full-text search, and counting). A fifty-year-old language keeps winning because the relational model matched how data actually behaves. Learn it once; bill it forever.

Run it yourself

With Postgres installed: createdb boringstack, then psql -d boringstack -f server/db/sql-from-zero.sql. The file ends with the two failing inserts commented out — run them by hand and read the refusals. psql itself is a boring gem: fifty years of interface refinement disguised as a plain prompt.

Check yourself

What does it mean that SQL is declarative?

You state the result you want — which columns, which rows, how grouped — and the database chooses the procedure. The JavaScript equivalent was hand-written loops; SQL hands the "how" to a planner with fifty years of tricks.

Why do reviews store question_id instead of the question text?

Normalization: one authoritative copy of each fact, referenced by id everywhere else. Copies drift; references can't. JOINs reunite the pieces at query time.

What did the foreign key and CHECK constraints each refuse, and why is the refusal the feature?

The FK refused a review of a nonexistent question; CHECK refused a result outside right/wrong. Refusal at the database layer means no code path, buggy or hostile, can store invalid data — invariants live where they can't be bypassed.

Our "what's due" JOIN returned five rows but was subtly wrong. How?

It listed every review on or before the cutoff, so questions appeared once per review instead of once with their latest schedule. The query answered what we said, not what we meant — the gap schema design closes.

What's the argument that SQL is the best effort-to-longevity trade on this roadmap?

Designed in 1974, still the dominant data language, with every replacement wave ending in the challengers adding SQL back. Skills learned once keep paying for decades — the boring-technology bet in its purest form.
