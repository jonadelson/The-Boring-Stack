JavaScript: The Language Under the Frameworks

Lesson 11 · javascript · ~10 min

JavaScript was designed in ten days in 1995, and has spent thirty years evolving under one absolute constraint: never break the web. Code from 1997 still runs. That's a deeply boring-stack virtue with a price — every early mistake is still in the language, permanently, next to the modern feature that fixed it. So practical JavaScript fluency isn't knowing everything; it's knowing which half to use. This lesson is that half, plus the handful of semantics that bite people arriving from other languages.

Declarations: two keywords, not three

Use const by default and let when rebinding is genuinely needed; both are block-scoped, like you'd expect. The third keyword, var, is a 1995 wart — function-scoped, hoisted, quietly global-prone — kept alive by the never-break rule. Recognize it in old code; don't write it. One trap in const: it freezes the binding, not the value. A const array happily accepts .push() — constancy of the name, not the contents.

Equality: one operator, and identity for objects

== coerces types before comparing, with rules nobody fully remembers (0 == '' is true). === compares without coercion. The boring rule: always ===, and the whole problem class disappears.

The deeper semantic: for objects and arrays, even === compares identity, not contents — {a: 1} === {a: 1} is false; they're two different objects. JavaScript has no built-in value equality for structures. If you're used to a language where data compares by value, this is the single biggest mental shift — and it's also exactly why React circles endlessly around "referential equality," memoization, and dependency arrays. That entire subculture is downstream of this paragraph.

Mutability: everything's open unless you discipline it

Objects and arrays are mutable, shared by reference, and passed around freely — any holder of a reference can change the data for everyone. The language won't stop you; discipline is cultural. The modern idiom leans copy-flavored: spread syntax ({...user, name: 'new'}) builds an updated copy, and newer array methods like toSorted() return fresh arrays where old sort() mutated in place. One caveat: spreads copy one level deep — nested objects inside are still shared with the original.

Closures: the feature this site already runs on

questions.forEach((details, index) => {
  button.addEventListener('click', () => {
    progress[keyFor(index)] = { result, ... };
  });
});

A function keeps access to the variables where it was defined, even when called much later from somewhere else. That's a closure, and you've already shipped some: in quiz.js, each click listener remembers its own index and details long after the forEach finished — ten listeners, each closing over different values. Closures are how JavaScript does what other languages need classes for: bundling behavior with the state it operates on. Event-driven code is closures all the way down.

this: the famous trap, mostly avoidable

In most languages, what this means is fixed where the code is written. In JavaScript, it's decided by how the function is called — the same function can see a different this per call, and a method handed around as a callback silently loses its object. Thirty years of bugs live there. The modern escape is pleasantly boring: arrow functions don't have their own this (they see their surroundings, like any closure), so use arrows for callbacks, shorthand methods on objects, and you'll rarely meet the trap. Notice quiz.js never mentions this at all — closures over plain data made it unnecessary.

The absent-value duo and its modern fixes

JavaScript has two nothings: undefined (never set) and null (deliberately empty). Historically they were handled with truthiness checks (value || fallback) — which misfire on legitimate falsy values like 0 and ''. The modern operators are precise: ?? falls back only on the two nothings, and ?. reaches into possibly-absent structures without throwing. quiz.js uses both: 

return JSON.parse(localStorage.getItem(STORAGE_KEY)) ?? {};
const result = progress[keyFor(index)]?.result;

One thread and an event loop

JavaScript runs your page on a single thread. Nothing interrupts a running function — which is why shared data needs no locks and a listener can update state fearlessly — but also why nothing else happens until it returns. The browser keeps a queue: your script runs to completion, then the next event's handler, then the next. Slow work therefore must not block; it's handed to the browser, which queues a callback for later. That model has a whole grammar — promises, async/await — that we'll learn when the phase 3 server gives us real waiting to do (network calls), where it stops being avoidable.

The boring truth: for years, "JavaScript development" meant compiling better languages into JavaScript — transpilers, polyfills, build pipelines. That era quietly ended. Since 2015 the language has absorbed its community's best ideas (modules, classes, spread, ??, ?., async), and every browser ships them natively. Written with taste — const, ===, arrows, the modern operators — plain JavaScript needs no build step at all. This site is the demonstration: view source shows the exact code the browser runs.

Check yourself

Why is {a: 1} === {a: 1} false, and what fashionable framework topic is downstream of it?

Objects compare by identity, not contents — these are two distinct objects. React's whole memoization/referential- equality/dependency-array discourse exists because re-created objects never equal their previous versions.

What does const actually make constant?

The binding — the name can't be reassigned. The value it points to is as mutable as ever: a const array can still be pushed to.

In quiz.js, how does each button's click listener know which question it belongs to?

Closure: each listener was defined inside a forEach iteration and permanently captures that iteration's index and details variables.

When does value || fallback misbehave, and what replaces it?

When 0, '', or false are legitimate values — they're falsy, so the fallback wrongly wins. value ?? fallback falls back only on null and undefined.

Why does single-threading make shared state easier, and what does it forbid?

No handler can be interrupted mid-run, so there are no data races and no locks. In exchange, nothing may block: slow work must be handed off and resumed via the event queue.
