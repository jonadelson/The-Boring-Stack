HTML: Thirty Years Old and Still Undefeated

Lesson 2 · html · ~6 min

If you've mostly worked in React or another component framework, you've probably treated HTML as the stuff your components compile down to — an output format, not a language you write. This lesson argues you've been skipping one of the most leveraged technologies in the whole stack.

Semantics: saying what things are

HTML's job is to describe what content is, not what it looks like. A page built from <div> and <span> says nothing; a page built from <article>, <nav>, <header>, and <main> tells browsers, screen readers, search engines, and reader modes exactly what they're looking at.

This very page is structured like this:

<article>          the lesson as a whole
  <header>         title and metadata
  <main>           the lesson content
    <section>      the quiz
    <aside>        callout boxes
  <nav>            previous/next links
</article>

Tap "view source" and check. Nothing on this page is a <div> — not because divs are forbidden, but because every piece of content here had a more specific element available.

The boring truth: semantic HTML is the cheapest accessibility work you will ever do. Screen readers navigate by landmarks and headings. Use real elements and you get a usable experience for free; use divs for everything and you'll spend weeks retrofitting ARIA attributes to rebuild what the elements would have given you.

The browser ships more than you think

A modern browser has built-in, no-JavaScript implementations of a surprising amount of UI:

  • <details>/<summary> — tap-to-expand disclosure (powering the quizzes on this site)
  • <dialog> — modal dialogs, with focus trapping
  • <input type="date"> — a native date picker
  • <datalist> — autocomplete suggestions
  • <form> validation — required, pattern, type="email", all enforced before submission

Each of these has been reimplemented thousands of times in JavaScript, usually worse: heavier, less accessible, broken on somebody's device. The boring-stack instinct is to ask "does the platform already do this?" before reaching for code.

HTML is fault-tolerant by design

Forget a closing tag and the page still renders. Use an element the browser doesn't know and it renders the content inside anyway. This wasn't sloppiness — it's why a page written in 1995 still works today, and why a page you write today will outlive every framework currently in fashion. Very few technologies offer a thirty-year compatibility guarantee. That is what "boring" buys.

Check yourself

What's the practical difference between a page of divs and a page of semantic elements?

They can look identical, but the semantic page is navigable by screen readers, understood by search engines and reader modes, and self-documenting to the next developer. The div page communicates nothing beyond its visual appearance.

You need a collapsible FAQ section. What's the boring-stack first move?

Check whether the platform already provides it — and it does: <details>/<summary>, no JavaScript required.

Why does HTML ignore errors instead of refusing to render?

Fault tolerance was a design goal: content should survive imperfect markup and decades of language evolution. It's a big part of why old pages still work and new pages degrade gracefully on old browsers.
