Progressive Enhancement: Build Down, Then Up

Lesson 13 · architecture · ~8 min

This site has now shipped JavaScript twice — quiz grading in lesson 10, home-page badges in lesson 12 — and both times the same sentence appeared: without the script, everything still works. That wasn't caution; it was a method with a name. Progressive enhancement is the practice of building a complete experience out of the sturdy layers first — HTML that works, CSS that presents it — and then adding JavaScript as an improvement on top, never as a requirement underneath. This lesson makes the method explicit, because from phase 3 on it becomes our architecture.

The argument is reliability, not ideology

The case for progressive enhancement is often misheard as concern for people who "turn off JavaScript" — a tiny audience, easily dismissed. The real argument is statistical: everyone is a no-JavaScript user occasionally. Scripts fail to arrive on flaky trains and hotel wifi; a CDN blip 404s a bundle; an ad blocker or corporate proxy eats a file; one uncaught error halts everything after it; an older browser chokes on new syntax. HTML has none of these failure modes — it renders as it streams, tolerates errors (lesson 2), and either arrives or the page doesn't load at all. When the page's function lives in the HTML layer, every one of those failures downgrades your site from "nicer" to "fine." When it lives in the JavaScript layer, they downgrade it to a blank screen.

The site as case study

  • The quizzes. The baseline is <details> — reveal-the-answer works with every script on earth broken. quiz.js injects the grading buttons, so the no-JS page contains no dead controls: nothing to grey out, nothing to apologize for. The enhancement carries its own UI in with it.
  • The home badges. Pure addition — read storage, annotate the list. Script absent: a clean lesson list, and nothing whatsoever is missing except a nicety.
  • The demo form (lesson 6). Validation, submission, keyboard behavior: all native. There was never a script to lose.

The method, as a checklist

  1. Spend HTML first. Ask what the platform already provides — <details>, <form>, <dialog>, a link. The native element is the baseline and the accessibility work, prepaid (lesson 9).
  2. Make the baseline complete, not a stub. The no-JS version must genuinely do the job, just less smoothly. A disabled button waiting for hydration is not a baseline; it's a ransom note.
  3. Enhance by addition. Scripts inject their own controls and intercept native behaviors (a form's submit, a link's navigation) rather than replacing the elements. If the script dies mid-way, the native behavior is still underneath, like a net.
  4. Treat JavaScript as a guest, not a host. Feature-detect before using the fancy API; parse storage defensively (quiz.js's try/catch); fail silent back to the working baseline, never loud into a broken page.

Where the discipline bends — and where it doesn't

Up the ladder, the baseline thins honestly: rung 3's HTML-over-the-wire keeps full-page navigation as its fallback almost for free, while a rung 4–5 tool — a canvas editor, a collaborative board — has no meaningful no-JS version, and pretending otherwise is theater. The discipline doesn't demand one. It demands that the boundary be drawn tightly: the island may require JavaScript; the page around it — the login, the docs, the settings, the billing (lesson 4's "80% edges") — still doesn't get to. Progressive enhancement is less a rule about scripts than a rule about honesty: never let the optional layer take the essential layer hostage.

The boring truth: the modern framework world spent a decade rediscovering this lesson at enormous cost. Server-side rendering, hydration, "islands architecture," React Server Components, the newer frameworks' love affair with plain <form> submissions — each is progressive enhancement being reinvented inside the tooling that abandoned it, with a build pipeline attached. The architecture phase 3 gives us — server-rendered pages, sprinkles on top — is where that industry-wide U-turn is heading. We'll simply start there.

Check yourself

Why is "nobody disables JavaScript anymore" not a rebuttal of progressive enhancement?

Because disabling was never the point: scripts fail circumstantially for everyone — flaky networks, CDN errors, proxies and blockers, one uncaught exception. The argument is reliability under partial failure, not sympathy for a setting.

Why does quiz.js inject its buttons instead of having them wait in the HTML?

So the baseline page contains no dead controls. If the script never runs, nothing broken is visible — the enhancement brings its own UI and takes it away with it.

What makes a no-JS baseline a "stub" rather than complete, and why does it matter?

A stub renders but can't do the job — a disabled button awaiting hydration. It matters because the whole guarantee rests on the baseline being functional: that's what every failure mode falls back onto.

How does the discipline apply to a genuinely JavaScript-dependent tool like a canvas editor?

The tool itself is exempt — no meaningful no-JS version exists. The discipline instead polices the boundary: the pages around the island (login, settings, docs) stay enhancement-based rather than inheriting the island's requirement.
