localStorage: The Smallest Database

Lesson 12 · javascript · ~8 min

Since lesson 10, your quiz answers have been living somewhere. This lesson is about that somewhere — the browser's built-in key-value store — and, along the way, your first meeting with the security boundary the whole web is organized around. There's also a new feature shipped with this lesson: the home page now shows your ✓ and ✗ counts next to each lesson. By the end you'll know exactly why that works and what its limits are.

The whole API fits in four lines

localStorage.setItem('key', 'value');
localStorage.getItem('key');    // 'value', or null
localStorage.removeItem('key');
localStorage.clear();

Persistent across reloads, tabs, and restarts. No setup, no permissions dialog, no library. The one quirk: both keys and values are strings, only strings — store a number and get back a string; store an object and get back "[object Object]", a classic rite of passage. Hence the convention quiz.js follows: JSON.stringify on the way in, JSON.parse on the way out, and structured data passes through a string-shaped hole intact.

Whose data is it? The origin

Here's the important idea hiding in the small API. Storage is partitioned by origin — the trio of scheme, host, and port (https://jonadelson.github.io). Every page on the same origin shares one store; pages on any other origin can't touch it, full stop. That's why the home page can read what eleven lesson pages wrote — same origin, same store — and why no other website can read your quiz scores or write fake ones.

Meet this boundary properly, because you'll see it everywhere from here on: the same-origin policy is the load-bearing wall of browser security. Cookies, fetch requests, iframe isolation — phase 4 is substantially about what the origin boundary protects and the attacks that try to reach across it. Storage is just its friendliest face.

A cache, not a ledger

localStorage's limits are worth knowing precisely, because two of them are why phase 3 exists:

  • ~5 MB per origin — plenty for preferences and progress, wrong for real datasets.
  • Synchronous — reads and writes block the one thread (lesson 11). Immaterial at our size; a reason the big-data alternative exists.
  • Erasable — "clear browsing data" wipes it, private tabs get a throwaway copy, and a browser under storage pressure may evict it. It is a convenience cache, and honest engineering treats it that way: nothing irreplaceable goes in.
  • Device-bound — the limit we keep meeting. Your phone and your laptop have never heard of each other. There is no code fix on this rung of the ladder; syncing requires a shared home for the data, and a shared home is a server. The phase 3 itch is now fully itching.

The neighbors, and when to knock

  • sessionStorage — same API, per-tab, gone when the tab closes. For "state of this visit," like a half-finished wizard.
  • Cookies — the elder mechanism, and mostly not a client-side store: cookies ride along on every HTTP request to the server. That's pure waste for data only the page needs — but exactly the point when the server needs it on every request, which is how sessions work and why cookies carry the web's logins. Phase 4 territory.
  • IndexedDB — the browser's big database: asynchronous, transactional, gigabyte-scale, and notoriously ceremonious. The boring rule: it exists for when localStorage genuinely hurts. A quiz tracker isn't that day; don't climb before the rung runs out.

The boring truth: even a 5 MB toy store deserves real data-modeling manners. The site's storage code keeps everything under one namespaced key (boring-stack:quiz) instead of scattering keys it can never confidently clean up; it parses defensively, because storage is user-editable and survives old versions of your code; and its keys carry an admitted flaw — they embed lesson URLs, so phase 3's URL redesign will force our first-ever data migration. Schema decisions have consequences at every scale. That's not a localStorage lesson; that's the Postgres lessons, rehearsed small.

Check yourself

Why does storing an object directly in localStorage fail, and what's the convention?

Keys and values are strings only — an object becomes "[object Object]". The convention is JSON at the borders: stringify going in, parse coming out.

What exactly is an origin, and what does it partition?

The scheme + host + port trio. It's the boundary of the browser's security model — storage, cookie access, and request rules are all partitioned by it. Same origin shares; cross-origin is walled off.

Why is "cache, not ledger" the right posture for localStorage?

Because it's erasable (user clearing, private tabs, eviction) and device-bound. Convenience data belongs there; anything irreplaceable needs a durable home — a server.

Cookies also store data — why are they the wrong tool for the quiz scores, and the right one for logins?

Cookies travel to the server on every request. For client-only data that's pure waste; for sessions it's the entire mechanism — the server needs the identifier every time.

You just edited your own quiz scores in dev tools. What's the general principle?

Everything client-side belongs to the user — storage, JavaScript state, the DOM. Sites must treat client-reported data as claims, not facts; servers re-validate.
