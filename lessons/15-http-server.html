A Web Server From Nothing

Lesson 15 · server · ~10 min

Phase 3 opens by puncturing a myth. "Web server" sounds like infrastructure — racks, daemons, other people's job. Here is the truth: a web server is a program that listens on a port, reads the four lines of text you met in lesson 5, and writes some text back. The repository now contains one — server/server.js, about forty lines of code, zero dependencies — and this lesson walks through it. If you have Node installed, node server/server.js serves this entire site from your own machine.

The whole shape of it

import { createServer } from 'node:http';

const server = createServer(async (request, response) => {
  /* runs once per request */
});

server.listen(3000);

That's a complete web server. listen(3000) claims a port — one of the numbered doors every machine has; the request handler runs for each arriving request, given two objects that are lesson 5 made tangible: request (the method, path, and headers the browser sent) and response (your side of the conversation — set a status, set headers, write a body, done). There is no magic underneath to find. This is the underneath.

While it runs, the site lives at http://localhost:3000 — and localhost just means "this machine, asking itself." Your phone can't see it; nobody can. Turning a program on your laptop into a name the whole internet can reach is a genuinely separate skill — DNS, deployment, TLS — and it's phase 5's opening act. For now the public site stays on GitHub Pages while the server grows up in private.

Serving files: what GitHub Pages actually is

Our handler maps the URL path onto a file under the site root, reads it, and sends it with the right Content-Type — the header you've been receiving since lesson 5, now written from the other side of the wire. Miss a file and the server decides what a 404 is. That's the entire secret of static hosting: GitHub Pages, nginx serving files, a CDN edge node — at heart, this same dozen lines with decades of hardening. Which reframes the last two phases: all along, "the server" was just a file-reading loop someone else ran. Now it's ours — and a program we own can do what a file-reader can't: accept data, remember it, and answer differently per person. That's the rest of phase 3.

The first attack arrives immediately

The moment you map URLs to files, you've created the oldest vulnerability on the web. What does your file-reading loop do with this? 

GET /../../../../etc/passwd

Resolve that path naively and it walks up and out of your site root, and the server cheerfully reads any file on the machine — directory traversal. The fix is in the source: resolve the path fully, then refuse anything that lands outside the root.

Testing it produced this lesson's best surprise. The obvious attack bounced before our guard ever ran — Node's URL parser resolves .. segments (even percent-encoded ones) during parsing. So is the guard dead code? No: a sneakier variant hides the slashes themselves as %2F, survives parsing intact, and becomes real path steps only on a later decode — and there the guard catches it, 403. Two independent layers, each covering the other's blind spot. Security people call it defense in depth, and the deeper posture behind it is phase 4's founding attitude, worth stating now: requests are not your friends. Every byte of every request is chosen by a stranger; a server that trusts its inputs is a server briefly.

The access log

2026-07-31T18:20:11.402Z 200 GET /index.html
2026-07-31T18:20:11.532Z 200 GET /css/style.css
2026-07-31T18:20:14.104Z 404 GET /nope.html

One console.log per request — timestamp, status, method, path. It looks like nothing; it's the ancestor of the entire observability industry, and the first thing you'll read when something breaks. Phase 5 treats logs properly; every server we write from here on keeps this habit from birth.

Two housekeeping notes

The repository gained a package.json — five lines, no dependencies. Its one meaningful entry is "type": "module", which lets Node use the modern import syntax. And note what installing this project looks like: git clone, node server/server.js, done. No npm install, no node_modules. Dependencies are debts; we'll take them on when they buy something (a Postgres driver will be worth it), and each one will be a decision, not a reflex.

The boring truth: a web framework is this file, grown up. Express and its kin are, at core: this request loop, plus a routing table (match method + path to a handler), plus middleware (functions that run before handlers), plus the file-serving we just wrote. All genuinely useful — and all things we'll now add ourselves, as the need arrives, so that if you ever adopt the framework, you'll know exactly which chores it's doing for you and roughly what they cost.

Check yourself

What is a web server, stripped of mystique?

A program listening on a port that reads an HTTP request — method, path, headers, maybe a body — and writes back a status, headers, and a body. Everything else is elaboration on that loop.

What does localhost:3000 mean, and why can't your phone open it?

localhost is the machine talking to itself, and 3000 is the port the server claimed. Nothing outside the machine can reach it — making a local program publicly reachable requires deployment, DNS, and TLS (phase 5).

What is directory traversal, and what's the defense?

A request path with .. segments that resolves outside the site root, tricking a file-serving server into reading arbitrary machine files. Defense: fully resolve the requested path, then refuse anything that lands outside the root.

Our guard never fires for a plain /../../etc/passwd — why keep it?

The URL parser neutralizes the obvious form, but an encoded-slash variant (%2F) survives parsing and becomes path steps on a later decode — the guard catches that one. Two layers covering each other's blind spots: defense in depth.

What can a server we own do that a static file host can't?

Accept and remember data (POST), and answer differently per request and per person — the abilities that make sync, accounts, and everything else in phases 3–4 possible.
