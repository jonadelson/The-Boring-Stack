HTTP: What Happens When You Tap a Link

Lesson 5 · http · ~8 min

Every framework, every API, every "full-stack" anything is a wrapper around the same conversation: a client sends a request, a server sends a response, and the connection forgets everything. That conversation is HTTP, it's made of readable text, and once you can picture it, half the mysteries of web development dissolve. Here's the whole journey, from tap to page.

1. The URL gets taken apart

https://jonadelson.github.io/The-Boring-Stack/roadmap.html
└─┬─┘   └────────┬────────┘ └───────────┬──────────────┘
scheme        host                    path

The scheme says how to talk (encrypted HTTP). The host says who to talk to. The path says what to ask them for. That's the whole anatomy — everything else (ports, query strings, fragments) is elaboration.

2. DNS turns the name into an address

Computers route by IP address, not by name, so the browser asks the Domain Name System: "who is jonadelson.github.io?" and gets back something like 185.199.108.153. DNS is a distributed, cached, forty-year-old phone book — and one of the purest boring technologies alive. It gets its own lesson in phase 5, when you'll point a domain at your own server.

3. A connection opens, then gets encrypted

The browser opens a TCP connection to that address, then performs a TLS handshake: the server proves its identity with a certificate, and the two sides agree on encryption keys. Everything after this point is unreadable to anyone in between. That padlock is the entire meaning of the S in HTTPS — same HTTP, wrapped in TLS.

4. The request: four lines of text

Here's what the browser actually sends. This is not pseudocode — this is the real protocol:

GET /The-Boring-Stack/roadmap.html HTTP/1.1
Host: jonadelson.github.io
Accept: text/html
Accept-Encoding: gzip

A method (GET: give me this; POST: here's data, do something with it), a path, and some headers — key-value metadata about the request. That's all a request is.

5. The response: status, headers, body

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Cache-Control: max-age=600
Content-Length: 6142

<!doctype html>
<html lang="en">
...

A status code, response headers, a blank line, then the body — the actual HTML. The status codes group by first digit, and knowing one or two per family covers daily life:

  • 2xx — success. 200 OK.
  • 3xx — go elsewhere. 301 moved permanently, 302 moved temporarily, 304 "your cached copy is still good."
  • 4xx — you messed up. 404 not found, 403 forbidden, 400 bad request.
  • 5xx — we messed up. 500 server error, 503 temporarily overloaded.

The boring truth: HTTP is plain text you can speak by hand. Run curl -i https://jonadelson.github.io/The-Boring-Stack/roadmap.html in a terminal and you'll see this site's real status line and headers. Or open your browser's developer tools, pick the Network tab, and reload this page — every request listed, every header inspectable. The entire web is debuggable with tools you already have.

6. Amnesia, by design

Here's the property that shapes everything to come: HTTP is stateless. When the response is sent, the server forgets you. The next request starts from zero — no memory of who you are or what you did. Statelessness is why the web scales (any server can answer any request), but it raises an obvious question: how does a site keep you logged in?

The answer is a header. The server says Set-Cookie: session=abc123, and the browser dutifully attaches Cookie: session=abc123 to every later request to that site — a name tag the server reads to "remember" you, one request at a time. That little mechanism carries the entire weight of login on the web, and building it properly — what goes in the cookie, how it's protected, how it's stolen — is most of phase 4.

Why this matters for everything ahead

The phase 3 server we'll write is a program that reads text like step 4 and writes text like step 5 — nothing more. Caching is a conversation in headers (Cache-Control, 304). Security headers are just more response headers. Sessions are cookies. When a framework misbehaves, the ground truth is always in the Network tab, because whatever the abstraction, this is what's actually happening.

Check yourself

What does it mean that HTTP is stateless, and what mechanism compensates?

The server forgets each client after every response; no memory carries between requests. Cookies compensate: the server sets one with Set-Cookie, and the browser sends it back on every later request, letting the server recognize you request by request.

A response comes back 404. Whose fault is it, roughly — and what about 503?

4xx means the request was the problem (404: asked for something that isn't there). 5xx means the server was the problem (503: it's overloaded or down for maintenance).

What's the difference between HTTP and HTTPS?

Nothing about the protocol itself — HTTPS is the same text-based HTTP conversation carried inside a TLS-encrypted connection, after the server proves its identity with a certificate.

Where do you look when you want to see the actual requests a page makes?

The browser developer tools' Network tab — or curl -i from a terminal for a single request with its status line and headers.
